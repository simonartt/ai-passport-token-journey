# Changelog

## 2026-10-04

- **Fixed a regression that broke the whole board, not just the new pages.** v1.1.8 read the two Hermes analytics responses (15–18 KB) into a 24 KB resident buffer, reasoning that a plaintext LAN request has no handshake memory peak. That reasoning was wrong: a resident static buffer is DRAM the heap can never have, handshake or not. This part has no PSRAM, and the v1.1.4 diagnostic recorded the largest contiguous free block at 29.7 KB — spending 24 KB of that left under 6 KB, and the first allocation to need it is the lwip DNS resolve PCB. So *every* provider started reporting `DNS`, not just Hermes, and the portal's httpd would not start either. The buffer is now 8 KB with a 7-day window (measured: usage 6.7 KB, models 4.8 KB, status 2.0 KB; at 30 days it is 17.8 KB and 14.7 KB). Nothing is lost on screen — page 3 shows no window length — but going back to 30 days now requires a streaming parser, not a larger constant. The two new pages (about 56 LVGL objects, roughly 12 KB of heap) are built when first shown and torn down on leaving; the data stays in memory and the page repaints from it on return.

- **New guard so this cannot ship twice.** `tools/check_mem_budget.py` fails the build if any resident static buffer exceeds 8 KB, and `tools/check_repo.py` runs it. Neither the host tests nor CI could see this one: both were green on a board that could not resolve a hostname. A memory budget has to be asserted like any other invariant.

- Two new pages put a local [Hermes](https://hermes.example) gateway on the card, so the board can show what the agent actually did rather than only what the three provider balances say. The card is now a four-page deck — TOKEN JOURNEY ↔ TOKEN BALANCE ↔ HERMES ↔ HERMES MODELS — walked with the DOWN key, with the page dots widened from two to four. **HERMES** (page 3) carries the agent avatar, a `TOKENS` figure, `CALLS` and `SESSIONS` right-aligned beside it, and a `GATEWAY / PLATFORMS` list whose four rows (feishu / telegram / weixin / discord) each carry a state dot and the live state word. **HERMES MODELS** (page 4) lists the top six models by token volume, each row with a rank, the name, the token count, `calls · provider` underneath, and a bar normalised to the leader. The numbers come from the gateway's own analytics: `GET /api/analytics/usage?days=N` (aggregated here into tokens / calls / peak concurrent sessions) and `GET /api/analytics/models?days=N`, plus `GET /api/status` for the platform states. The gateway measures agent traffic through the gateway — including locally hosted models that cost nothing — so it is a **different unit from the balance pages and is deliberately not summed into the renminbi total**; it gets its own page instead.

- Talking to the gateway takes two steps, because its `api/*` endpoints do not accept a `Basic` header — they require the session cookie a browser login produces. The device now performs `POST /auth/password-login {"provider":"basic",…}` once, keeps the returned `hermes_session_at` cookie in RAM, sends it on the two analytics requests, and re-logs-in once if a `401` comes back. The gateway is addressed over plain HTTP on the local network, so unlike the provider fetches this leg needs no TLS handshake. Configuration (address, user name, password) is a new section on the portal config page, stored as three NVS keys under `cfg` (`hbase`/`huser`/`hpass`); leaving the password blank keeps the stored one, matching the existing incremental-save semantics. `/diag` reports whether a gateway is configured and which of the three responses arrived.

- **Fetch ordering.** The whole Hermes chain runs **after** the provider balances and after the exchange rate, never before them. This is the v1.1.6 lesson applied: two slow non-critical requests in front of the slowest host cost that host its row. A gateway that is slow, unreachable or not configured must not be able to delay a balance.

- Parsing lives in a new pure module `main/we_hermes.{h,c}` (host-tested, no ESP dependencies): it extracts the daily aggregates from `analytics/usage`, the heaviest models from `analytics/models`, and the gateway plus platform states from `status`. `tests/test_we_hermes.c` asserts against real captured responses, including the large-payload path. Small buffers that could truncate under `-Werror=format-truncation` were widened (`err` 8→16, `raw` 20→24, `meta` 40→52) rather than left to a silent cut.

- The avatar is compiled in as `main/hermes_avatar.h`, a 104×104 1-bit `LV_COLOR16` image generated from the source SVG by `journey-web/gen-avatar.cjs` (resvg) — the same route the lock screen portrait already takes, so no PNG decoder is needed. It is a `const` array, so it lives in flash and costs no RAM. Generated on a transparent background with the figure in the accent colour, which keeps it on-palette.

- When nothing came back, both pages show `HERMES FAIL` plus a short tag (`TOUT` / `401` / status / `NOCONF` when no gateway is configured) instead of a screen of `--`. The `GATEWAY / PLATFORMS` heading is a fixed string: a degraded gateway changes its colour, not its length, so the heading can never overrun the 212 px text column.

## 2026-10-03

- OpenRouter balances are US dollars; the other two providers are renminbi, so a card that reads "5.00" next to one that reads "146.09" cannot be summed or compared. When any USD-priced provider is configured, the device now fetches the live USD/CNY rate (frankfurter.dev first, open.er-api.com as backup — both return a tiny JSON and both sit on certificates inside the built-in CA bundle) and converts the dollar amount to renminbi before display, before the daily ledger, and before the 30-day heat map, so all three platforms total in one currency. The rate is cached to NVS (`cfg`/`usdcny`, scaled by 1000) and reused if both live sources fail; the last resort is a fixed 6.800. `/diag` prints the rate and its source (`live`/`cache`/`default`). Converting the stored baseline means a rate change alone can show a cent-scale phantom "spend" on days the balance did not move — the accepted cost of a single-currency ledger that can total across providers.

- A configurable auto-refresh interval: the portal's config page gained an "auto refresh" dropdown with Off / 30 / 60 / 120 / 180 minutes. The chosen value is stored as a single byte (`cfg`/`refmin`) and read when the board is entered; the existing 60-second heartbeat refreshes on that cadence instead of the old fixed 10 minutes. "Off" still retries when the last read failed and still honours a manual short-press; only the periodic online refresh stops. The interval logic (`we_set.{h,c}`) is pure and host-tested.

- The TOKEN JOURNEY and TOKEN BALANCE page coordinates are now named macros consumed by the layout (title, hairline, summary card, heat grid and today cell, LOW/HIGH legend and the four swatches, page dots, both battery pills), with compile-time assertions tying the macro table to the grid geometry so a hand-edit cannot silently drift. The balance-page battery pill moves to match the journey page (174,11,50,19); the legend swatches drop 3 px to sit centred against the LOW/HIGH labels.

## 2026-10-01

- Diagnose balance refreshes instead of guessing at them. Screen text only ever said `DIRECT FAIL`, which is true for a DNS failure, an unreachable host, a TLS handshake failure, a rejected certificate, an invalid key and a changed response schema alike. The new `main/we_diag.{h,c}` records a snapshot of every refresh — the stage it reached, and per provider the `esp_err_t`, the mbedTLS error code, the certificate verification flags, the HTTP status, a response-body preview, the attempt count and timing, plus free/minimum heap and the largest free block (a TLS handshake on this PSRAM-less part is bounded by the largest block). A failing row now shows a short tag where the amount would be (`DNS`, `CONN`, `TOUT`, `TLS`, `X509`, `401`, `JSON`, `NOKEY`, `NOSTAT`) and the status line reads `DIRECT FAIL 401`. The portal gained `GET /diag`, a plain-text page behind the same Basic Auth (`no-store`) that prints that snapshot together with the configuration actually in effect — Wi-Fi SSIDs, per-provider key length and last four characters, and an explicit warning when a stored key contains whitespace or control characters. It is linked from the config page so the trace can be copied off the phone.

- API keys are sanitized on save and again immediately before each request: ASCII whitespace and control characters are dropped and a copied-along `Bearer ` prefix is stripped. A key pasted with a trailing newline otherwise travels inside the `Authorization` header, which servers reject as a malformed request — on screen that is indistinguishable from a wrong key. A value that is whitespace only counts as "not filled in" and leaves the stored key alone, matching the incremental save semantics.

- Refresh hardening: when a first pass returns nothing from any provider the fetch set is retried once (`FETCH_TRIES`), the refresh worker stack grew from 6 KB to 8 KB because an mbedTLS handshake on this part is stack-hungry, and SNTP now configures three servers (`CONFIG_LWIP_SNTP_MAX_SERVERS=3`, so `ntp.aliyun.com`, `cn.pool.ntp.org`, `time1.cloud.tencent.com`) because a single unreachable or firewalled NTP host silently leaves the clock unsynced.

- Corrected a wrong claim from the previous entry. ESP-IDF 5.5.3 defaults `CONFIG_MBEDTLS_HAVE_TIME_DATE` to `n`, which means certificate expiry is *not* verified by this build at all — the clock was never the reason a TLS handshake failed. Syncing the clock before the first request is still the right order (the `UPDATED` line, the ledger day boundary, and it doubles as a DNS/UDP reachability probe), but it is not what fixes `DIRECT FAIL`.

- Host tests: added `tests/test_we_diag.c` (error and status tag mapping, snapshot round-trip, overlong-string clamping, tiny/NULL buffers) and extended `tests/test_we_cfg.c` with key sanitizing and incremental key update cases; `tools/validate.sh` runs the new suite.

- Fixed a bug in the diagnostics themselves (v1.1.3): the esp-tls classification code (`0x8000` range, which says *which layer* broke) is the **return value** of `esp_http_client_get_and_clear_last_tls_error()`, not an out parameter. The code treated a non-zero return as a failure flag and zeroed the out params — so on a genuine connection failure the `/diag` page always reported `tls_code = 0`, exactly when it mattered. The classification code is now kept in `we_diag_row_t.tls_err`, and `we_diag_tag_from_pair()` picks the more informative of the two error codes for the on-screen tag (the classification code beats the blanket `ESP_ERR_HTTP_CONNECT 0x7002`). Also added a standalone network probe: when a whole refresh round fails, the same connection path is re-run with `esp_tls` in `is_plain_tcp` mode (DNS + TCP only, no handshake, no large buffers — also a low-memory probe) using an owned error handle, separating `0x8001` (hostname unresolved) / `0x8004` (TCP refused) / `0x8006` (timeout) plus the socket errno (111 refused / 110 timeout / 101 no route / 113 host unreachable / 104 reset), alongside a snapshot of the local IP, gateway and DHCP-assigned DNS servers. The probe section in `/diag` finally explains what `0x7002` actually means.

- The v1.1.3 diagnostics caught the real culprit behind `DIRECT FAIL`, and it is now fixed (v1.1.4): a live `/diag` readout showed `heap: free=81444 min_free=176 largest_block=29696` — 81 KB free in total, but the **largest contiguous block was only 29.7 KB**, and the historical minimum free heap once fell to **176 bytes**. The mbedTLS handshake allocates a single 16 KB receive buffer (IDF default `CONFIG_MBEDTLS_SSL_IN_CONTENT_LEN=16384`) plus a 4 KB send buffer, and that allocation simply fails on a fragmented heap, which is exactly what the bare `TLS` on-screen tag meant. The upstream firmware carries none of the community edition's resident overhead (mDNS, portal, backup, diagnostics), so the same device had no trouble handing-shake — that is the full explanation for "the original connects, ours doesn't". The fix is entirely at the sdkconfig level, no fetch logic changed: RX buffer 16384→6144 (the balance API response is a few hundred bytes and certificate chains run about 4 KB; a single TLS record rarely exceeds 4 KB), TX buffer 4096→1024 (the request body is empty, only a ClientHello goes out), and the peer certificate is no longer kept after the handshake (another ~4 KB). Together that trims roughly 17 KB off the handshake peak. The `/diag` heap line now flags "largest block insufficient, handshake will most likely fail" whenever the largest contiguous block drops below 24 KB.

- Added an OpenRouter provider adapter (v1.1.5): `GET https://openrouter.ai/api/v1/credits`, remaining balance = `total_credits − total_usage` (USD, two decimals). Three things to know: the endpoint **requires a Management Key** (generate one on the OpenRouter Keys page; ordinary inference keys `sk-or-v1-…` get 403); OpenRouter sits behind Cloudflare with a Google Trust Services certificate — direct connectivity from mainland China tested fine, though it will never be as stable as DeepSeek/Kimi; the on-screen amount is in **USD**, so it cannot be directly summed with the CNY amounts of the other two providers. The config page gained a third key row. Also investigated duoyuanx.com (a new-api v0.12.6 relay): its OpenAI-compatible billing endpoints (`/v1/dashboard/billing/subscription` + `/usage`) could yield a balance, but they require two requests and a subtraction, and the balance page/ledger currently has only 3 card slots (extending to 4 means migrating the NVS ledger blob), so it is not added in this release.

## Unreleased

- Fixed the balance page reporting `DIRECT FAIL` right after provisioning, which had two independent causes. First, saving the portal form rebuilt the configuration from an empty struct instead of merging into the stored one, and the form never pre-fills the API-key or Wi-Fi-password inputs — so submitting the Wi-Fi-only form silently wiped every provider key and the refresh had nothing left to query. Saving is now an incremental merge over the stored config (`we_cfg_set_wifi` / `we_cfg_set_prov_key` / `we_cfg_del_prov`): a blank field keeps the current value, a blank Wi-Fi password reuses the saved password for that SSID, and dropping a platform requires ticking its new remove checkbox. Provider rows now state whether they are configured (showing the last four key characters) and warn that leaving them blank keeps the key, and saving a config with zero provider keys logs a warning. Second, the SNTP wait ran *after* the balance fetch loop, so the first refresh reported no `UPDATED` time and the ledger day boundary was derived from a 1970 clock; the clock is now synced before the first request. (This entry originally blamed the certificate bundle for rejecting every server certificate as not yet valid — that was wrong, see the 2026-10-01 entry.) When no provider key is configured at all the page shows `NO API KEY` instead of the misleading `DIRECT FAIL`.

- Firmware builds now succeed from a clean checkout: `tools/validate.sh --firmware` reconfigures to pull the managed components, re-applies the `esp_lvgl_port` FAP_SCREENSHOT_V1 capture-hook patch (`scripts/patch-esp-lvgl-port.py`), and only then compiles, because `managed_components/` is untracked and a fresh dependency resolve overwrites the patched sources. Added `.github/workflows/build-firmware.yml` and `.github/workflows/static-checks.yml` so a tag push builds and publishes the merged firmware, with `espressif/mdns` pinned to 1.13.1 for reproducible component resolution. The patcher matches anchors by code shape and aborts the build when one is missing, instead of writing a half-patched file — a half-patch still compiles and only surfaces later as an undefined `lvgl_port_display_set_snapshot_cb` at link time.

- Configuration and ledger backup/restore over the portal: `GET /backup` downloads one JSON document holding the whole `we_cfg` blob (nickname, Wi-Fi profiles, provider API keys) plus the `balhist` ledger (per-provider daily baselines, 31 days), and `POST /restore` writes both back to NVS and reboots. The two blobs are written together on purpose — `hist_check_rows()` wipes the whole ledger whenever the provider order stops matching `row_id`, so restoring keys alone would silently drop the heatmap. The ledger data model moved to the new shared header `main/we_hist.h` so the added `main/we_backup.c` can read that NVS blob without reaching into `app_balance.c` internals. Wi-Fi and API-key fields that do not fit their slot are rejected instead of truncated, a rejected restore leaves NVS untouched, balances are rounded to four decimals on export so the file stays readable, and `days` is emitted in ascending date order. The config page gained a backup section (download link plus file upload) and the HTTP server stack grew to 8 KB.

- Config portal now runs on the local network instead of a captive AP: the device first tries the saved WiFi profiles as a station and shows the LAN address plus an mDNS name (`http://token-journey.local/`) on screen; it only falls back to the `BAL-XXXX` SoftAP when every profile fails or nothing is configured yet, so a brand-new device can still be provisioned. The portal now requires HTTP Basic Auth (`admin` / `12345678`) because a LAN-reachable page can rewrite configuration, and it closes itself after five idle minutes so the WiFi radio is not held on (a station link costs roughly 80-100 mA). Added the `espressif/mdns` component, made `demo_radio_network_prepare()` tolerate `ESP_ERR_INVALID_STATE` so the portal and the balance refresh can share the network stack, and let the balance refresh skip a cycle while the portal owns the radio.
